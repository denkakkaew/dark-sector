# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Dark Sector** — an alien-shooting arcade game built in **Godot 4.6** (GL Compatibility renderer, Jolt physics for 3D). **Every storyboard screen now exists**: `Title.tscn` (set as `run/main_scene`) → sign-in → `SceneRouter` runs briefing → fact card → quiz → battle → scene cleared through all four destinations to the win text → `Results.tscn`, the ranked board persisted by the `Leaderboard` autoload. `Game.tscn` is the battle — a reticle-aimed turret firing lasers at alien ships in four flight modes, over a per-scene sky, lighting and planet backdrop, with Mars' armoured ore carrier. Phase 9 added the polish layer: sound and music (`Audio` autoload over a **placeholder** set), screen shake, touch/hold to fire, an idle reset back to the title (`IdleWatch`), and the title's four-destination attract cycle. A web build is exported under `docs/` for GitHub Pages, a Windows preset builds to gitignored `build/`, and the gdUnit4 test addon is installed. **Every phase in the plan is done** — what's left is the art pass, real sound files, and the tuning judgements that need a human at the kiosk. See `planning/STORYBOARD.md` for the full spec and `planning/IMPLEMENTATION_PLAN.md` for the phased roadmap and each phase's "Still unverified".

Target deployment: a single **16:9 landscape touchscreen on Windows**. Design and test for touch input and that fixed aspect ratio first; mouse is only a development stand-in.

**This branch is the Thai build.** Every player-facing string — screens, HUD, cards, and all 20 fact/question sets in `CampaignData.gd` — is Thai, the sign-in screen types Thai, and the UI font is a Thai one. What stays Latin is deliberate and short: the "DARK SECTOR" wordmark, "ISS", the version stamp, and the debug-only scene-jump hint. `planning/` and every code comment stay in English; they are for whoever maintains this, not for the kid at the kiosk.

## Game design (the spec to build toward)

The player mans a **turret** and shoots invading alien ships heading for Earth, following the aliens' invasion plan and breaking it at every link. It is also an **educational game for kids ~8–12**: each scene teaches one real space fact. The full screen-by-screen design lives in `planning/STORYBOARD.md`, and the player's path through the screens is: title → sign-in → (per scene) briefing → fact card → quiz → gameplay → scene cleared → … → victory or game over → results/ranking.

- Aliens attack across a **4-scene story campaign** (1 scene = 1 level), with difficulty rising each scene: **ISS (first contact) → Moon (alien forward base) → Mars (aliens mining fuel) → Earth orbit (final stand)**. Score, timer, and quiz tally carry across the whole campaign; energy does not.
- An **energy bar** decreases whenever an alien ship gets through ("getting through" means reaching the station/base or escaping with ore, per scene); if it hits zero, the game ends. Its starting level each scene is set by the pre-battle quiz answer (it does not carry between scenes).
- **Educational layer:** each scene's mission briefing shows one true "DID YOU KNOW?" space fact; a multiple-choice **quiz** on that fact runs *before* the battle and sets starting energy — correct = full bar + bonus score, wrong = partial bar (~70%) with the correct answer shown, no other penalty. Facts and questions live in a per-scene data table so content is extensible. Each scene holds a **pool of five** fact+question variants and draws one per run (avoiding the one it drew last time), so a kiosk replayed back to back keeps teaching something new.
- Aliens fly in varied patterns — **direct / strafe / weave / swoop** — introduced scene by scene; Mars adds a slow, armored, high-value **ore carrier**.
- Some scouts **attack the turret itself with an electric shock** (`shock_chance` per wave, rising each scene; carriers never do). A shocker that flies within range of the gun slows almost to a hover, turns to face it and crackles with a swelling blue orb for a second — the easiest shot it will ever offer — and if it survives it discharges a lightning bolt: the gun is **jammed** (won't fire, shudders, sparks, reticle stutters blue) for ~1.2 s and the bar loses a fraction of a leak. The jam is the real cost, deliberately; see `CampaignData.SHOCK`.
- Clearing all 4 scenes wins, showing the message **"เย้!! เราปกป้องโลกไว้ได้แล้ว!"** — the storyboard's verbatim "Yay!! We protected Earth!" in Thai. It is still a fixed line, not a sentence to re-word.
- Supporting systems the build needs: a **sign-in screen** before play, a **timer**, and a **ranking/leaderboard** system (persisted locally in a `user://` file).

When adding features, keep these three subsystems (sign-in, timer, ranking) as distinct concerns — they outlive any single level and likely belong in autoload singletons rather than per-scene logic.

## Engine configuration (already set in `project.godot`)

- Renderer: `gl_compatibility` (desktop and mobile both) — stick to features supported by this renderer; avoid Forward+/Mobile-only rendering features.
- 3D physics engine: **Jolt Physics**.
- Windows rendering device driver: `d3d12`.

## Working in this project

- Open in the editor: `godot --editor --path .` (or `godot -e`). The Godot 4.6 editor is the primary tool — most scene, node, and resource wiring happens through the UI, not by hand-editing `.tscn`/`.tres` files. (Note: `godot` is not currently on this machine's PATH — locate/confirm the Godot 4.6 binary or launch from the installed editor.)
- Run the game from CLI: `godot --path .` runs `run/main_scene`, `res://scenes/Title.tscn`. Pass a scene path as a positional argument (`godot --path . res://scenes/Quiz.tscn`) to boot straight into one screen; the briefing also has dev keys 1–4 to jump scenes.
- Run tests: gdUnit4 is installed (`addons/gdUnit4/`); tests live under `tests/`.
- Export a Windows build: `godot --headless --path . --export-release "Windows Desktop" build/windows/DarkSector.exe` — the preset exists; `build/` is gitignored. The web build goes to `docs/` for GitHub Pages: `godot --headless --path . --export-release "Web" docs/index.html`. A **release** export is also what drops the briefing's dev scene-jump keys, which are gated on `OS.is_debug_build()`.
- `.godot/` is generated cache (gitignored) — never edit it; delete it to force a reimport if assets get stuck.

## Conventions

- GDScript files use `.gd`; scenes `.tscn`; resources `.tres`. Prefer scenes + GDScript unless there's a reason to add C# (no C# / .NET is configured here).
- Cross-scene state (current scene, energy, score, quiz tally, signed-in user) lives in **autoload singletons** registered under `[autoload]` in `project.godot`, not passed manually between scenes: `GameState` (game flow + state/signals), `Leaderboard` (`user://leaderboard.json` persistence), `SceneRouter` (every screen transition), `Audio` (all sound) and `IdleWatch` (returns an abandoned kiosk to the title), loaded in that order. Note that autoload identifiers do **not** resolve in a script run with `-s` that replaces the main loop — flow harnesses have to run as a scene.
- **Sound goes through `Audio.play("name")` and nothing else** — never a path, never an `AudioStreamPlayer` in a gameplay scene. A sound whose file is missing is a `push_warning` and silence, deliberately, so a kiosk never stops for it; that also means a typo is invisible, which is why `tests/audio_test.gd` lists every name the code calls and checks it against the disk. Add a `play()` call, add the name to that list. Every `BaseButton` gets its click automatically when it enters the tree (opt out with the `silent_button` group); the music bed is picked by `SceneRouter._go_to()` and nowhere else.
- The files under `assets/audio/` are **placeholders** written by `tools/gen_placeholder_audio.py` (Python stdlib only, seeded so re-running doesn't churn the repo). Replace one by dropping a `.wav` with the same name in the same folder — no code changes. Regenerate with `python tools/gen_placeholder_audio.py`, then let Godot reimport.
- The attract stills (`assets/backdrop/destination_1..4.png`) are **photographs of the real `Game.tscn` scenes** with the HUD hidden. Re-shoot them if the scene looks change, or the title advertises a game that no longer exists. Three screens show them now: the title cycles them (`AttractBackdrop.gd`), and the briefing and fact card each hold their own scene's still behind the text (`DestinationBackdrop.gd`, which owns the shared `IMAGE_PATH`). Those two are read at 28–30px over the picture, so they layer a gradient `Scrim` over it and hold it at a lower `image_alpha` than the title does — turn either knob if a photograph starts winning against the words.
- **All Thai text is drawn with `assets/font/ui_font.tres`**, set as `gui/theme/custom_font` in `project.godot`. Godot's built-in font has no Thai glyphs whatsoever, so if that setting ever stops resolving the engine falls back to it and *every screen in the game fills with tofu boxes* without a single error — which is why `tests/thai_localisation_test.gd` checks the setting, loads the font and asserts a glyph for every letter Thai is written with. The resource is a `FontVariation` over Noto Sans Thai (OFL) with a `SystemFont` fallback for the UI symbols (▶ ✔ 🏆 ⌫ ★ ↻ ⎋ ⌂ ◄) that no Thai text font carries. Gotcha worth knowing: `variation_opentype` keys must be the **integer** OpenType tag (`2003265652` for `wght`), never the string `"wght"` — a string key is accepted, saved back out, and silently ignored, and the font just draws at its default weight.
- Thai sets a **taller line box than Latin at the same point size** — tone marks stack above the letter and vowels below it. Anywhere a screen packs many lines into a fixed 648px, that difference accumulates into a row of controls pushed off the bottom edge; `Results.tscn` and its `ROW_FONT`/`HEADER_FONT` were retuned for exactly that. Screenshot a screen after changing its text, rather than trusting that it still fits.
- The sign-in screen's on-screen keyboard is **Thai (Kedmanee), generated from `SignIn.KEY_ROWS`** — six rows, 67 keys, because the shift layer is laid out flat instead of behind a shift key a child would get stuck on. It carries every consonant, vowel and tone mark a name is spelled with, which the tests enforce along with the per-row key budget that keeps it on screen. `ALPHABETICAL_ROWS` beside it is the same 67 keys in the ก ข ค order a Thai child recites; swapping the two is a one-word edit and a test proves they stay interchangeable. Kedmanee is ordered by typing frequency, so if kiosk observation shows kids hunting for letters, that swap is the fix.
- Per-scene content (story line, fact card, quiz, spawn table, backdrop) belongs in one **campaign data table** (`CampaignData.gd`) that briefing, fact card, quiz, HUD, and spawner all read from — adding a fact or a 5th scene should be a data change, not a code change. A scene's `quiz` is an array of self-contained `{fact, question, answers, correct}` entries; append one and it joins the draw. Vary which slot the right answer sits in — a test enforces it, because kids find "it's always the first button" long before they find any astronomy.
- **The quiz variant is drawn once per scene, by `SceneRouter.show_briefing()`**, and held in `GameState.quiz_variant` until the next scene. The fact card screen shows the fact and the quiz asks about it, so every screen that touches it must read the same pick (`GameState.quiz_entry()`) — never roll one in a screen's `_ready()`. `tests/screen_flow_test.gd` greps both reading screens for `roll_quiz_variant` to keep it that way. `GameState._last_quiz_variant` deliberately survives `reset_campaign()`: like `player_name`, it belongs to the kiosk rather than to the run.
- A scene's battlefield backdrop is the `look.photo` block in that table: drop an image in `assets/backdrop/`, point `texture` at it, and `tint` it down so it stays scenery and the aliens stay the brightest thing crossing it. `SceneLook.gd` hangs it on the one quad authored in `Game.tscn`, keeping the quad's hand-tuned width and taking its **height from the image's own aspect** — so images of different shapes crop rather than stretch. A `texture` path that doesn't resolve is a `push_warning` and a scene with no backdrop, same deliberate silence as a missing sound, which is why `tests/campaign_data_test.gd` checks every path against the disk. A scene whose photo paints its own ground (Mars) wants `bodies: []` — a procedural sphere in front of a painted horizon just cuts it in half.
- Current layout: gameplay scenes in `res://scenes/` (`Game`, `Turret`, `AlienShip`, `Laser`, `HitEffect`) and their scripts in `res://scripts/`. Extend these rather than recreating them; keep the `scenes/`–`scripts/` split.
- Hand-editing a `.tscn` to give a script a node reference (`@export var x: SomeNode`) needs
  `node_paths=PackedStringArray("x", …)` on the `[node …]` line as well as the `x = NodePath(…)`
  property. The editor writes both; writing only the property fails **silently** — the export
  stays null, nothing errors, and the feature just doesn't happen. `scenes/Game.tscn`'s
  `SceneLook` node is the worked example.
- **The shock is split three ways**, like a leak: `AlienShip` runs the charge and draws the bolt (`_update_shock`, emits `shocked_turret`), `Game._on_turret_shocked` applies the cost (`Turret.stun` + `GameState.take_damage`, so the HUD's edge pulse and the camera knock come for free), and `Turret` owns the jam. Lightning is `ShockArc.gd` — camera-facing triangle ribbons, because GL Compatibility draws every line one pixel wide. `tools/Shoot.tscn -- 1 out.png shock` flies one shocker at the turret and saves a frame every 0.1 s. The two shock sounds draw from their own RNG in `gen_placeholder_audio.py` so adding them didn't rewrite the rest of the set — do the same for any sound added later.
- Stay within GL-Compatibility renderer features — prefer `CPUParticles3D` over `GPUParticles3D`, avoid Forward+/Mobile-only effects.
- **The turret, alien fleet and ISS deck are regenerated models** (3D-generator downloads, not the old Tripo/.blend sources), exported by `blender/export_rebuild.py` — **read this before the older bullets below, which describe the pipeline that made the previous versions.** The raw downloads live in `temp/` (gitignored, Godot-ignored via `temp/.gdignore`, left out of both export presets); only the exported `.glb`s under `assets/` ship, so the export cannot be re-run on a fresh checkout. Every generator model arrives **normalised to 1.0 unit on its longest side**, so real size is part of the export (`SPECS` in that script: `size`, `yaw`, or a hand-set `euler_deg` + `scale`), and glass domes are dropped by the generator. Run it headless — `"<blender>/blender.exe" --background --factory-startup --python blender/export_rebuild.py [-- name ...]` — and never via the Blender MCP with `read_factory_settings`, which unloads the MCP add-on. `blender/scene_rebuild_prompts.md` holds every image prompt and the object list for the rebuild of all four scenes.
- The generated models are **not axis-aligned**: a ship's nose can sit 30–55° off the model's own axes, and bounds will not tell you. When a hull looks wrong in flight, don't re-derive it — `blender/make_fleet_adjust.py` builds `temp/alien_fleet_adjust.blend` (the exported ships beside a flight arrow, the turret and a ruler), a person turns/scales each ship by hand, and `blender/read_fleet_adjust.py` prints the result for `SPECS`. That is how the gunship and heavy cruiser got their `euler_deg`/`scale`.
- **Hit boxes are per hull.** `AlienShip._fit_collision_to()` measures the hull a ship wears (its vertices, not a transformed AABB) and sizes the collision box to it; the box in `AlienShip.tscn` is only a placeholder. The ore carrier sets `hull_override` to its own model rather than drawing from `AlienShip.HULLS`. The turret is two models, `turret_base.glb` and `turret_gun.glb` (origin at the trunnion axis); `Turret.tscn` hard-codes the pivot and muzzle that the export prints, and `Game.tscn` seats the turret into the deck by the amount `export_rebuild.py` documents. The deck (`iss_hull_deck.glb`) is a full ring built from three 120° wedges around a round pad, centred on the turret's seat.
- **Godot's headless `--import` rewrites `project.godot`** (strips the comments, the gdUnit plugin entry and the viewport/aspect settings). It is needed to refresh the cache after re-exporting a model, so back the file up first and restore it afterwards, and check `git diff project.godot`. `tools/Shoot.tscn` boots the real battle scene and saves a PNG (`-- <scene 1-4> <out.png> [lineup|strafe|play] [top|side|close]`) for judging how a model sits in the game.
- **A scene can be a 3D set instead of a painting.** `look["set"]` names a .tscn that `SceneLook` hangs under `Set` (and drops on the next scene); `look["photo"]["distance"]` pushes the painted backdrop far back along its own ray (bigger and further, so it looks identical) and it stays only as the sky. The star field (`look["stars"]`, on only for Earth) goes back with a pushed sky, to just in front of it, so stars land behind the set rather than on it. Both are optional, so a scene without them is unchanged. **All four scenes are 3D sets now (1 ISS, 2 Moon, 3 Mars, 4 Earth).** **Earth:** `scenes/sets/EarthSet.tscn` (from `blender/earth_layout.py` via `make_earth_set_scene.py`) is a night city seen from above — everything hangs under a `City` node `SET_Y` = −120 m below the deck, so the 4 m-high camera looks *down* on it as the painting does, and the sky plate is pushed to 3 km because the city runs to 1.5 km (anything behind the sky quad is hidden). `blender/build_earth_set.py` builds the street-grid ground, ~8,000 filler buildings in one mesh, the river, elevated light-trail roads and a golden cable-stayed bridge; **nothing is lit by a lamp — all the glow is material emission from textures** (a window atlas, a street grid, a lane of headlights) over near-black walls, with each building's UVs scaled by its own size. The three generated towers and one mid-rise are exported by `export_rebuild.py` with `emissive` set, so their own lit-window texture is also their emission. (`earth_building_midrise_b` was generated too but is 1.96M faces of separate window islands that no decimation here gets under ~150k, so the layout uses the first mid-rise twice; `export_rebuild.py` has `dissolve`/`min_polys` knobs for models like that.) **Earlier scenes:** ISS/Moon/Mars notes follow.  **Mars:** `scenes/sets/MarsSet.tscn` (from `blender/mars_layout.py` via `make_mars_set_scene.py`) — the generated colony (dome, ring-decked tower, pods, radar dish, rovers, crawler), the alien drill rig with its crane, ore piles and six drones (which *work*: `scripts/Worker.gd` walks each to random spots near its post, stops to lean and swing its pick, and wanders on — procedural movement of the rigid model, seeded per drone, no collision; tuned by `DRONE_ROAM_RADIUS`/`DRONE_WALK_SPEED` in `mars_layout.py`), plus Blender-built (`build_mars_set.py`, which reuses the Moon's terrain tools) rust-sand ground with flat-topped mesas, stacked-slab sandstone ledges framing the corners, scattered rocks and tilted solar panels, in front of the generated orange sky plate. The ledges are solid stepped outcrops (each stratum a prism reaching into the ground; the templates draw from their own RNG so reshaping them never moves a ledge). **Ships climb over rock instead of through it:** set nodes in the `flight_obstacle` group (Mars' `Ground`, `Ledges`, `Rocks`, tagged by `make_mars_set_scene.py`) are ray-cast once per scene by `FlightFloor.gd` into a height map of the flight zone, which `SceneLook.flight_floor` holds and the spawner hands each `AlienShip`; the ship looks ahead along its real track and lifts off its course to clear it (`CLEARANCE`, `LOOK_AHEAD`), then sinks back. Tag a new set's near rock the same way. Mars is also the one scene with **haze**: `look["fog"]` (colour + density) sets the Environment's exponential fog, which fades the far mesas toward the sky's horizon colour; the sky quad always opts out of fog (`disable_fog`).  The ISS keeps its painted Earth limb as the backdrop (a 3D globe can't match its sharpness across half the screen) pushed back to `distance` 220, with `scenes/sets/ISSSet.tscn` — generated by `blender/make_iss_set_scene.py` from `blender/iss_layout.py` — in front: just the generated `iss_module`, drifting slowly left to right below the turret (`scripts/Drift.gd`, 2 m/s, wraps at x=±80) at y=-5, z=-30, i.e. under the alien flight lanes. **The Moon:** `scenes/sets/MoonSet.tscn` is *generated* by `blender/make_moon_set_scene.py` from `blender/moon_layout.py` (move things there, not in the .tscn), the ground/ridge/rocks/pad/pipes by `blender/build_moon_set.py` (procedural, headless), and the alien-base buildings by `export_rebuild.py`. The ground is real geometry (craters, the horizon ridge) under a seamless tiled regolith texture with a vertex-colour multiply — and deliberately gentle across the whole ~36 m spawn zone so no ship spawns inside a hill. Everything tall stays beyond the spawn ring (base 55–90 m out). Six of Mars' drones (the same model and `Worker.gd`) work the landers and tanks — `DRONES` in `moon_layout.py`. The ground out there rolls by ~0.3–0.5 m inside a drone's beat, so the Moon's drones set `Worker.ground` (to `Terrain`; the generator writes the `node_paths` it needs) and keep their feet on it by ray-casting the terrain, which they measure once between them; they also hop higher (`bounce`) for the low gravity.  `blender/scene_rebuild_prompts.md` lists what each needs.
- The game starts **fullscreen** (`window/size/mode=3`, exclusive); the viewport and the "keep" aspect still letterbox the 16:9 picture.
- 3D art comes out of Blender via a checked-in export script, not a manual File > Export. That's `blender/export_turret.py` (run it from Blender's Scripting tab, or `exec(open(...).read())` in a Blender MCP session). It measures pivots from the geometry, re-origins each part, decimates to a triangle budget and caps texture sizes — the raw Tripo models are ~2.4M tris with 170 textures and cannot ship as-is. It prints the pivot/muzzle offsets that `scenes/Turret.tscn` hard-codes, so re-run it after editing the model and update the scene if those numbers move. Source scenes are never modified: it works on throwaway copies.
- That script also finishes Tripo's raw output, which ships flat matte (roughness 0.9, no metallic) and unbalanced. `TEXTURE_GRADE` and `SURFACE_FINISH` name the parts to treat: textures are white-balanced onto the turret's average hue, levelled and given a gentle contrast curve in linear space, and the BSDF gets a lower roughness so large curved surfaces catch a form-defining highlight. Balancing is measured per *collection*, not per part — collections from the same Tripo run can carry opposite casts. Keep metallic low: GL-Compatibility has no reflection probe or sky here, so metal has nothing to reflect and goes black.
- `PARTS` in that script maps each export to the Blender collections it's built from: `gun` and `base` (the turret, to `assets/object/turret/`) and `hull` — the curved ISS station surface the turret is bolted to, built from `ISS_TurretBase1`/`2`, written to `assets/object/iss/`. The hull is exported on the *pedestal's* pivot, so it drops into Godot already lined up with the turret rather than needing to be positioned against it by hand. Its on-screen framing is then tuned purely through the `ISSHull` node's scale in `Game.tscn`.
- `blender/export_alien.py` is the companion script for the alien saucer (`AlienShip.blend` → `assets/object/alien/alien_ship.glb`), same pipeline, different subject. Two things differ deliberately. It decimates harder and caps textures smaller (9k tris, 256px) because several aliens are alive at once, where the turret is a single instance. And it applies `SURFACE_FINISH` but **no** white balance: that grade exists to make the player's own hardware read as one material family, and pulling the aliens' purple hull and green pilot onto the turret's grey would throw away the strongest colour contrast on the gameplay screen. It also joins every part into one mesh, so an alien is one node in the scene tree instead of 61, and yaws the model so the pilot faces Godot's +Z — the direction the ships fly. It prints the bounds that the collision shape in `scenes/AlienShip.tscn` is sized to, so re-run it after editing the model and update the scene if they move.
- An alien is drawn from a **pool of three hulls** (`AlienShip.HULLS`), one picked per ship as it spawns, so a wave arrives as a mixed fleet. `blender/export_alien_variants.py` exports the other two straight from the raw Tripo `.glb` downloads in `planning/`, driving `export_alien.py`'s pipeline rather than repeating it — so a change to how the ships look is still made in one place. `alien_ship.glb` is deliberately not re-exported by it: that one comes from `AlienShip.blend`, the download *plus* hand cleanup. Every hull is exported centred on its own bounds, facing +Z and inside the same footprint, which is what lets `AlienShip.tscn` hold one collision shape and no per-hull transform. Adding a fourth is an export plus a line in the array.
- Which way a model points is the one thing that genuinely differs per ship, and it is recorded in that script's `FACING` table. **The saucer faces +X in the .blend** — check it in Blender's Numpad-3 (Right) view, where you should be looking the pilot in the face, and don't infer it from the bounding box: the saucer is nearly as wide as it is long, so which axis is longer flips with small edits and says nothing about which end is the nose. Get it wrong and the ships fly home tail-first, which is only obvious close to the camera — at spawn distance the face is a few pixels and either orientation looks the same. Park one in front of the camera to check, or render the four sides headless and find the view you are looking the pilot in the face from — which is how the other two were settled.
- Tripo does not hand back a consistent material set, and the difference bites. Some models arrive with a basecolor map only; others carry a packed metallic/roughness map and a normal map too, and because `SURFACE_FINISH` is only written into sockets that *aren't* already linked, those ships keep Tripo's own values — metallic 1.0 included, which on GL-Compatibility renders as a black blob. `_base_colour_only()` strips every map but base colour before the finish is applied, so the whole fleet takes its look from the same two numbers.
- `TRI_BUDGET` buys less than its name suggests — it is divided by the source's *face* count, and Tripo's meshes are quads — and it is not one size fits all. Smooth curves collapse gracefully; flat plating does not. The plated disc (`alien_ship_3.glb`) shatters into shards at the saucer's budget, so it carries its own `budget` in the variants table. Judge this by rendering the decimated model, not by the triangle count: the count barely moves across the knee.
- Files are UTF-8 (`.editorconfig`).
